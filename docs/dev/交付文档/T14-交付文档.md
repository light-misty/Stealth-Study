## 1. 功能范围与任务清单

07 §4 T14 原文写「`service.py` + `routes.py` 追加 I1-I6」。三点口径先行说明（诚实登记，
详见 §5-1/§5-2）：

* **I2/I3 已由 T13 交付**（`GET /automation-templates`、`POST /automation-templates/{tpl_id}/install`），
  本阶段不重复实现；
* **I1（`GET /v1/campus/personas`）不在本阶段范围**：T13 §6-1 建议它随 T21 人设清单，但 T21
  实际以 GUI 既有端点 `GET /v1/personas`（`ss/server/app.py:260`）验证了六人设可见性，campus
  侧 I1 至今未落、归属仍未收敛（§6 移交）；
* **本阶段交付 I4-I6 三行 + INF-03 导入恢复**，与 VERIFY 报告 §2 对 T14 未实现状态的登记
  （「无 exports 相关实现，仅 `EXPORT_NOT_FOUND` 已预登记」）精确对应。

实际交付 **3 个端点 + 恢复能力**：

| 组 | 端点/能力 | 需求 | 要点 |
|---|---|---|---|
| I4 | `POST /exports` | INF-02 | `{profile_id, format: "md"\|"json"\|"csv"}` → `{filename, path}`，落 `state_dir()/campus/exports/`；json 为全库备份包，md/csv 为单档案人读面（§5-3/§5-4）；文件名全生成、永不冲突（同秒加 `-2/-3` 后缀） |
| I5 | `GET /exports/{filename}` | INF-02 | 文件流 + `Content-Disposition: attachment`；媒体类型按扩展名（md/json/csv）；`EXPORT_NOT_FOUND` 统一应答，不泄漏存在性差异 |
| I6（裸） | `POST /exports/wipe` | PRD §7.3 | 02 §7.1 一键清除：删 `campus.db`（含 `-wal`/`-shm`/`bak-v*`）+ `campus/` 整树 → 重建空库，返回 `{wiped: true}`；与 A10 共用同一清除实现 |
| I6（恢复） | 同端点 + `{restore_filename}` | INF-03 | 07 §2「I6 为 I4 的逆过程」（03 §4.9 与 07 的口径调和见 §5-2）：坏包在毁灭发生前全量校验 → 按**包自身版本**重建空库 → 单事务回放 → `migrate()` 升到当前版本（低版本包产生迁移提示）→ 返回 `{wiped, restored, schema_migration}`；`campus/exports/` 保留（§5-5） |

json 备份包结构（02 §7.4「单 JSON 文档，19 张表各一数组，`schema_meta.version` 一并写入」）：
`{kind, schema_version, exported_at, row_counts, tables}`——`tables` 为 18 张数据表
（`schema_meta` 不回放，其版本以字段承载）各一数组，`row_counts` 供恢复后逐表对账。

md 报告结构（本阶段定义，§5-9）：标题（档案名）+ 导出时间/轨道/状态/考试信息 + 八段
（学习进度、知识点掌握、题库与作答、错题本、词汇、复习队列、学习计划、考试节点）。
csv 为该档案作答流水（attempt 12 列，utf-8-sig 便于 Excel 直开）。

### 3.2 开发中发现并修复的问题

1. **schema_meta 不在迁移链内**（测试先行捕获）：`_rebuild_schema` 最初只跑 `_MIGRATIONS`，
   而 `schema_meta` 由 `migrate()` 用独立 DDL 创建——恢复请求在 `INSERT INTO schema_meta`
   处 `no such table` 崩溃。修复：重建路径先执行 `SCHEMA_META_DDL`。
2. **坏包删库后失败的数据丢失窗口**（边界审计发现，`b6436d2`）：包内同表重复主键能通过
   原校验，却在删库之后的回放阶段才因 PRIMARY KEY 冲突失败——此时现行数据已毁。修复：
   主键唯一性纳入破坏性 wipe 之前的全量校验；新用例 `duplicate_id` 钉死「拒绝且不清库」
   （该用例对无守卫实现具有判别力：旧实现下 profile 计数断言为 0 ≠ 3）。
3. **Windows 双连接下 wipe 的文件占用**（测试形态问题，非产品缺陷）：初版测试 fixture 与
   路由各持一个 `CampusStore` 连接，`wipe()` 删库文件被另一连接占用（WinError 32）。生产为
   单连接（test_mount 门约束挂载唯一），测试改为「种子连接先关→请求→断言连接后开」的
   `_SoloWipe` 形态，并在文档串记录该约束。

## 5. 与文档的差异登记

1. **07 T14 的「追加 I1-I6」为过期口径**：I2/I3 已由 T13 交付；I1 仍无归属（T21 以 GUI
   既有 `GET /v1/personas` 完成人设可见性验收，campus 侧 I1 未落）。本阶段按 VERIFY §2
   的 T14 登记交付 I4-I6。
2. **I6 的双重身份调和**：03 §4.9 定义 I6 = 一键清除；07 §2 INF-03 定义 I6 = 导入端点
   （I4 的逆过程）。两文档冲突，实现为**同一端点两态**：无 body = 纯清除（03 口径原样）；
   带 `{restore_filename}` = 清除 + 恢复（07 口径）。前端 T15 的 `wipeCampusData()` 发空
   body，03 形状不受影响；03 §4.9 I6 行已回流补注。若主理人倾向"导入独立端点"，属契约
   变更（新增非 72 行端点），需另行拍板。
3. **验收①「三格式可重新导入」的落点为 json**：02 §7.4 明确导入格式是「单 JSON 文档」，
   md/csv 无任何文档定义其包结构。落法：json = 全库可恢复包；md = 人读学习报告；csv =
   人读作答流水。md/csv 不可恢复是契约使然而非能力缺失；行数一致以 json 回导逐表对账满足。
4. **json 包为全库而非单档案**：I4 的 `profile_id` 对 md/csv 是内容范围，对 json 是请求
   上下文校验。理由：INF-03 是备份恢复、I6 恢复是空库重放——若包体单档案，恢复会静默
   丢弃其他档案与 `app_state`，属意外数据丢失；02 §7.4「19 张表各一数组」本身即全库口径。
5. **恢复保留 `campus/exports/`**（只清 `campus/library/`）：02 §7.1 纯清除删整树；恢复
   若同删会把刚用作恢复源的备份一并销毁，与备份恢复目的相悖。
6. **迁移提示的形态是结构化字段**：`schema_migration: {from, to}`（无迁移为 `null`），
   不发文案字符串；前端渲染属 T17+ 范围。验收②的"提示"以此字段为数据源。
7. **`SCHEMA_VERSION_ERROR` 沿用 500 档**：03 §6 表注「实际发生在启动期，此处为防御性」
   正是本导入路径；不另立 4xx 码，避免契约漂移。
8. **恢复后 `source_doc`/`doc_chunk` 行指向已删除的 library 原件**：02 §7.4 的包只含 19 表
   数据，不含 `campus/library/` 文件本体；恢复会清该目录。V0.1 无 B 组消费面（资料库端点
   未交付），无用户可见影响；**B 组交付或 V0.2 前必须**决定：包体外挂 library 文件、或
   恢复后将 `parse_status` 标为待重析。已登记为移交项（§6-4）。
9. **md 段落结构与 csv 列集为本阶段定义**（02/03/04 均未规定内容结构）；csv 取 attempt
   流水是"最大平表 + 表格软件可用性"的工程判断，产品侧可后续调整（仅改 `_attempts_csv`）。
10. **`Idempotency-Key`（03 §1 幂等约定）未并入 T14**：T09 §5-11 与 VERIFY §7-5 建议
    「并入 T14 或单列小任务」。不并入的理由：请求头级幂等缓存需键值存储 + TTL，19 表
    契约（02 §1.2）已锁定、加表属契约变更；且 I4（全库包幂等重放）与 I6（清除幂等）的
    防重复目标在内容层已满足。建议单列小任务并由主理人确认存储方案（V0.2 或 T23 后）。
